## Next small options, not implemented

1. **Build the full-body core-index lookup once per publication, not twice.** The full-pose lambda clears25 `CoreSlots` and performs the same ten `BodyNames.IndexOfByKey(UpperCoreBoneNames[...])` lookups on each invocation (`3770–3775`). It is called twice with unchanged manager layout and no intervening callbacks. Moving this integer-only lookup immediately outside the lambda cuts its rebuilds in half without any persistent cache or invalidation mechanism. Keep the last-duplicate assignment behavior of the current loop and keep every pose calculation inside the lambda unchanged. This is a modest candidate bounded by the0.7821 ms whole publication sample.

2. **Cache each sampled training rotation within one physical resample.** `QuatToMatrix` normalizes a quaternion, constructs its matrix and narrows matrix components to float (`311–319`). Resampling repeatedly applies `MirrorYBasis(QuatToMatrix(ActualTransforms[Index].GetRotation()))` to pelvis, leg bones, ten core bones and their shared parents, and both arms (`2681–2695`, `2796–2825`). There are31 such source-level conversions with ten core bones; some indices repeat. A fixed25-entry array plus per-call filled flags can lazily reuse the exact computed `FMat3f` for each required body index. Cache only within the function after the actual pose read; do not cache across physics steps, carriers or source edits. This preserves each conversion's math and all cleaning, tolerance, recurrent-state comparisons/copies, and physical-sample counters. Do not compute all25 unconditionally if fewer are consumed; a lazy cache avoids new work for unused calf/lower-arm rotations. It needs an oracle comparison across lower/upper state arrays and nonzero tolerances, not only displayed bone checks.

3. **Retain layout indices across manager resample/publication only if the simpler changes matter.** Both resampling (`2798`) and full-pose construction (`3774`) search the same policy name layout. `BodyNames` and `Parents` come from the runtime contract (`1907–1910`); `UpperCoreBoneNames` is rebuilt/validated when the upper contract is loaded (`2118–2127`). A manager-owned integer map built on successful contract load could remove these searches. The existing exact-layout `ProphecyCrowd::FNameIndexLookup` is an alternative if live in-place layout validation is desired. Preserve first `IndexOfByKey` semantics and reverse-map last assignment semantics; invalidate on every contract/layout rebuild. No pose/matrix/value cache is needed.

4. **Separate physical pose read from pure resampling only after measuring the split.** `ResamplePhysicalAgentState` performs one actual `SampleActualComponentPose` into an existing25-transform slice (`2675–2679`). Its remaining state/matrix/tolerance/recurrent calculations use manager-owned plain arrays/structs; sampling through a Jolt character reads completed world transforms and converts them into the current inherited AgentMesh frame (`ProphecyJoltCharacterComponent.cpp:918–935`). A future staged GT sample + blocking pure parallel resample could use the same ownership approach as completed-pose batching, preserving per-agent buffers and aggregating counters after join. This is larger than the lookup/matrix reuse options and the current timer does not say how much of0.9729 ms is sampling versus pure math. Add one temporary nested read/math diagnostic before choosing it. Do not drop the actual pose sample, reduce cadence or reuse a prior feedback frame.

## Visual-root constraints

`UpdateVisualRoots` interpolates root/yaw and calls the actual `AProphecyAgent::SetManagedRootLowPoint` every presentation frame (`3982–3996`). That function rotates the capsule carrier, performs a swept location move, handles penetration/slide and returns `Hit.bBlockingHit` (`ProphecyAgent.cpp:3125–3172`). The manager's conditional branch intentionally performs blocked-root recurrent-state correction; it is not a generic movement-success branch.

No proven duplicate whole-pose work exists on the unobstructed path. The two transform mutations may cause repeated component/bounds/overlap propagation, but replacing them with a combined move or deferred `FScopedMovementUpdate` can change rotation-before-sweep semantics and public callback timing. That is not a safe deletion or cache under the current requirement. Do not skip capsule sweeps, overlap handling, root correction, slash handoff, or its necessary corrected-source publication. The useful next diagnostic is separate time/call counts for `SetManagedRootLowPoint` versus its correction branch, preserving all operations.

The old negative debug-mesh lookup was already changed to allocation-free FName construction, and remains a live `FindObjectFast` so removal or appearance of a debug component is observed (`1775–1795`). No new long-lived negative cache is proposed.

## Preserve these seemingly repeated operations

- Do not remove `CleanState`/`CleanUpperState` before or after tolerance application just because the input matrices were normalized earlier. They act at different stages, and repeated float orthogonalization can change the exact recurrent comparison branch (`2707`, `2827`, `2886`, `2919`).
- Do not replace zero tolerance with a raw-state bypass: the current matrix-to-quaternion/Slerp/normalization path still cleans the represented rotation. That requires an explicit oracle proof rather than an identity assumption.
- Do not reuse the previous publication's current component pose as the new previous pose without accounting for physical feedback, root rebasing, walk/run policy changes and slash overlay. The current previous/current source states may be edited independently between publications.
- Preserve30 Hz model/resample updates,60 Hz presentation, all25 policy bones, all88 completed skeletal bones, all22 native query bodies and real capsule movement. The full NN rerun after the deletion is the next evidence gate.
