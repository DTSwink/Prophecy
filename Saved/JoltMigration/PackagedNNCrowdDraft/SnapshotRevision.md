This is a procedure for the parent to review and execute. No snapshot, source, build output, or existing report was modified while writing it.

The current failed snapshot is `Saved/JoltMigration/NNCrowd-20260909-144331-647/snapshot.json`. Its owned project remains the sibling `Project` directory. The only authorized source replacement is `Source/GameAnimationSample3/Private/ProphecyPhysicsBenchmark.cpp`, after replacing the two editor-only `ClassGeneratedBy` queries with `GetClass()->HasAnyClassFlags(CLASS_CompiledFromBlueprint)` in reviewed active source.

## Source correction

UE 5.7.4 source confirms `UClass::ClassGeneratedBy` is behind `WITH_EDITORONLY_DATA` (`Runtime/CoreUObject/Public/UObject/Class.h:3832–3835`). `CLASS_CompiledFromBlueprint` is an unconditional class flag describing classes generated from Blueprint material (`Runtime/CoreUObject/Public/UObject/ObjectMacros.h:243–244`). `UClass::Serialize` saves and restores it with `ClassFlags`; its transient-flag removal mask does not remove this bit (`Runtime/CoreUObject/Private/UObject/Class.cpp:6015–6027`). Runtime engine code uses `HasAnyClassFlags(CLASS_CompiledFromBlueprint)` (`Runtime/Engine/Private/BlueprintGeneratedClass.cpp:1500`). It therefore supports the intended actor contamination guard and count in Editor, Development Game, and Shipping.

## Minimal revision procedure

1. Wait for every build/cook/game process using this owned project to end. Do not replace source while UBT or AutomationTool is running. Keep all existing manifests, logs, controls, staging directories, and failure reports.
2. Run `Read-NNSnapshot` on the original manifest before mutation; this verifies every recorded input. Hash the original manifest and the failed package report. Read the reviewed active CPP and hash it before and after copying. Verify the source diff is exactly the two approved Blueprint-flag replacements. Reject any additional changed input or unreviewed source edit.
3. Retain the original `snapshot.json` bytes. Prepare a new manifest by copying its data in memory, retaining `schema: 1`, the same `projectDirectory`, `projectFile`, original source/config provenance, engine/dependency/model hashes, and all unchanged input entries. Add `revision: 2`, a fresh creation timestamp, and `revisionProvenance` containing the predecessor manifest absolute path and SHA256, the failed report absolute path and SHA256, the reason, and the one changed relative path with old/new hashes. Add an explicit limitation: the predecessor describes the failed r1 project state and is superseded for further builds; the mutable project directory now represents r2.
4. Resolve the absolute replacement destination and verify it is exactly the recorded CPP under the owned `Project` directory. Copy only that reviewed active CPP there. Set its destination `LastWriteTimeUtc` to the current UTC time, then verify the destination bytes against the captured new hash and that the active source hash stayed unchanged. Preserve `Binaries`, `Intermediate`, dependency installs, existing stages, and cook/build caches. This lets UBT reuse valid outputs while recompiling the changed translation unit.
5. Update only that input entry's `source`, `bytes`, `sourceLastWriteUtc`, `sourceSha256`, and `snapshotSha256` from the reviewed active file. Keep `readOnlyCopy` and all other entries unchanged. Rehash every manifest input against the resulting project before writing the new manifest. Write the new sibling `snapshot-r2.json` with create-new semantics; never overwrite the original manifest or an existing revision. If interrupted after replacement, record the incomplete revision and stop; do not present the old manifest as valid for the modified project.
6. Validate `snapshot-r2.json` through the unchanged `Read-NNSnapshot`. It accepts an arbitrary filename provided that its parent is the parent of the owned `Project` directory. The old manifest will intentionally fail its CPP hash against the revised project; that is expected history, not permission to rewrite the old record. The new manifest's predecessor hash keeps that record verifiable.
7. Run the existing Development packaging wrapper against `snapshot-r2.json`. It creates a new package/report/stage directory, rebuilds the snapshot Editor and Game targets, and reruns the controlled query tests against the new snapshot hash and Editor DLL. The prior r1 controls or failed package are not acceptance evidence for r2. Run the r2 Development executable and validator; only its passing runner can authorize the same-r2 Shipping wrapper and runner.

No fresh project copy, asset/config rewrite, broad source resynchronization, cache deletion, or altered package identity is needed. Original failed evidence remains intact; r2 metadata states the intentional one-file mutation. Timestamp freshness requests recompilation, and the resulting UBT action log remains the evidence that it occurred.
