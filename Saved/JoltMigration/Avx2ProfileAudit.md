# Optional AVX2 Jolt profile: read-only audit

2026-09-09. No dependency/source edits, compilation, downloads, or UE processes were performed for this audit. The working SSE2 profile remains the baseline. This is preparation for an explicit local performance experiment, with no claimed speedup.

An AVX2 build is feasible, but replacing the native DLL alone is invalid. Jolt's double-vector argument type changes between SSE2 and AVX, so the native library and every translation unit including Jolt headers must use the same effective ISA macros. A startup check inside the existing AVX2 module cannot reject unsupported CPUs before DLL loading.

## Why ABI and macro agreement are mandatory

- Pinned [MathTypes.h:20-24](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/Math/MathTypes.h:20) defines `DVec3Arg` as **by-value `const DVec3` with AVX**, and **`const DVec3&` without AVX**. The public native `BodyInterface` APIs use the corresponding `RVec3Arg`, including position/rotation, kinematic motion and point impulses. This is a concrete C++ signature difference, not only an optimization preference.
- [DVec3.h:19](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/Math/DVec3.h:19) changes its underlying SIMD representation from two `__m128d` values to one `__m256d`. Both x86 profiles keep 32-byte double-vector alignment; equal size/alignment alone does not certify compatibility.
- [Core.h:146-183](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/Core/Core.h:146) derives AVX, SSE4.2, SSE4.1, F16C, LZCNT and TZCNT from AVX2. They are effective requirements even if individual CMake options are left OFF.
- [Jolt.cmake:937-979](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/Jolt.cmake:937) explicitly exports ISA definitions to consumers and selects `/arch:AVX2` for MSVC. Our external UBT module must reproduce this contract because it does not consume Jolt's CMake target transitively.
- `JPH_VERSION_ID` in [Core.h:68](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/Core/Core.h:68) includes precision/determinism/assertion and other ABI feature bits, but **does not include SIMD ISA or FMA**. Keep `VerifyJoltVersionID`, but do not use it as proof of SSE2/AVX2 agreement.
- `GetConfigurationString()` is [inline in ConfigurationString.h](C:/Users/singerie/Documents/Unreal%20Projects/Prophecy/Intermediate/JoltMigration/Upstream/Jolt/ConfigurationString.h:11). The current startup log reports the consumer's compilation, not an independent native-DLL feature fingerprint. A small exported POD build-contract accessor compiled into the DLL would provide that independent check after safe admission. It can be added through the project CMake wrapper without modifying the pristine upstream checkout.

For the AVX2 profile, set `MinCpuArchX64 = MinimumCpuArchitectureX64.AVX2` on **ProphecyJolt**, and publish the complete matching JPH definitions through **ProphecyJoltLibrary**. Setting it only on the external library module does not configure the consumer translation units. UE's [ModuleRules.cs:944](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Programs/UnrealBuildTool/Configuration/ModuleRules.cs:944) exposes this module setting; [UEBuildModuleCPP.cs:2626](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Programs/UnrealBuildTool/Configuration/UEBuildModuleCPP.cs:2626) applies the current module's value. [VCToolChain.cs:1046](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Programs/UnrealBuildTool/Platform/Windows/VCToolChain.cs:1046) emits `/arch:AVX2` and `PLATFORM_ALWAYS_HAS_AVX_2=1`; therefore an AVX2-compiled guard cannot safely assume its own code is baseline-compatible.

## FMA and precision

`USE_FMADD=OFF` plus `/fp:precise` does **not** ensure an FMA-free stock MSVC AVX2 build. `Core.h:175-183` automatically defines `JPH_USE_FMADD` when `__AVX2__` is present unless `JPH_CROSS_PLATFORM_DETERMINISTIC` is defined. Explicit `_mm*_fmadd_*` paths in `Math.h:51`, `Vec3.inl:355` and `DVec3.inl:421` remain enabled regardless of the precise compiler switch. Defining `JPH_USE_FMADD=0` is also ineffective because the code checks whether it is defined.

Two honest stock profiles are available:

1. **AVX2 + precise + FMA:** explicitly enable the effective SSE4.1/4.2/AVX/AVX2/F16C/LZCNT/TZCNT/FMADD options, leave AVX512 off, preserve current double/single storage, solver settings and precision compiler flags. FMA changes rounding and can improve arithmetic accuracy; it does not reduce model precision, body count, solver iterations or cadence. Functional validation is still required; trajectory identity is not an acceptance gate.
2. **AVX2 + precise + cross-platform determinism + no FMA:** enable stock `CROSS_PLATFORM_DETERMINISTIC`, leave FMADD off, and match its public macro in the consumer. This avoids a private upstream patch. It is a separate arithmetic profile, not an ISA-only A/B: e.g. `Vec3.inl:900-915` also changes signed-zero handling in SSE4.1 reduction. No physical quality reduction is required, but speed cannot be inferred.

If the narrow aim is stock AVX2 performance, option 1 is the smaller change. If no FMA is a strict constraint, option 2 is the supported stock route. Do not silently label option 1 as no-FMA, or silently enable determinism merely to make that label true. Neither option needs fast-math, reduced precision, reduced cadence or retuned PHAT angles.

## CPU validation must precede AVX2 module loading

The existing plugin loads at `PreDefault` and the game statically imports its public symbols. UE's [ModuleManager.cpp:1173](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Runtime/Core/Private/Modules/ModuleManager.cpp:1173) loads the module/import dependencies before running generated registration/static initialization and finally `StartupModule` at line 1236. [WindowsPlatformProcess.cpp:204](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Runtime/Core/Private/Windows/WindowsPlatformProcess.cpp:204) resolves this through native DLL loading. Monolithic imports load before the game entry point. Consequently, adding `HasAVX2InstructionSupport()` at the start of the existing AVX2 module is useful diagnostics but is **not** a complete pre-DLL safety boundary.

The smallest local-only experiment is a separate **baseline-compiled CPU preflight executable**, invoked by the explicit AVX2 launcher before starting Unreal/game. It must not link any Jolt module/DLL and must reject unknown/unsupported capability before launch. A checked local build is not a self-contained portable executable; launching that AVX2 editor/game directly would bypass its external guard.

Required evidence from preflight: x64; SSE4.1/4.2 and POPCNT; AVX plus OSXSAVE and XCR0 XMM/YMM state `(XCR0 & 6) == 6`; AVX2; BMI1/TZCNT and BMI2 because MSVC `/arch:AVX2` may emit them; F16C; LZCNT from extended CPUID; FMA if the selected profile enables it. Do not execute XGETBV before OSXSAVE is known. Record the raw supported/required masks and selected profile, rather than infer support from the processor marketing name.

UE's baseline [WindowsPlatformMisc.cpp:3294-3428](C:/Program%20Files/Epic%20Games/UE_5.7/Engine/Source/Runtime/Core/Private/Windows/WindowsPlatformMisc.cpp:3294) already shows a suitable cached AVX/OS-context/AVX2/BMI/POPCNT test. `HasAVX2InstructionSupport()` includes OS context and BMI1/BMI2, but its feature table does not independently test the FMA bit or extended LZCNT bit; it is insufficient by itself to fingerprint the entire proposed stock Jolt profile. Its F16C bit can be checked separately.

A later portable in-process selector requires a genuine baseline bootstrap with **no normal import of either AVX2 consumer or Jolt**, then explicit loading after CPU checks. Normal-imported Jolt allocator/Factory data prevents simply adding delay-load to the current module. That architecture is larger than the requested performance experiment and should not be introduced just for this diagnostic.

## Preserve SSE2 artifacts and archive provenance

Use one explicit build-time profile for each process. Keep existing `Build/{Configuration}`, `Install/{Configuration}` and `ProphecyJolt_5_6_{Configuration}` untouched as SSE2. Add separate proposed `Build/AVX2/{Configuration}`, `Install/AVX2/{Configuration}` and `ProphecyJolt_5_6_AVX2_{Configuration}` names; add a further suffix if testing both FMA and deterministic/no-FMA. Require the same selected profile in the CMake recipe, external module and consumer module. Prefer a tracked selector included in both modules' `ExternalDependencies`, rather than an untracked environment-variable change that could reuse a stale UBT makefile.

Before switching: stop UE/game normally, preserve current consumer binaries/receipts and their hashes as well as the SSE2 dependency, then rebuild the consumer against the chosen import library. Distinct native DLL names prevent accidentally selecting a staged SSE2 DLL, but the UE `UnrealEditor-ProphecyJolt.dll` name itself is unchanged: profile-specific dependency folders alone do not preserve a runnable prior consumer. Do not switch ISA through Live Coding or load both implementations into one process with mixed ownership/Factory globals. Reverse the profile and rebuild/restore the known matching consumer to return to SSE2.

## Bounded acceptance experiment

1. Baseline CPU preflight and explicit profile provenance pass; unsupported/unknown CPU path fails before launch. Record toolchain, pinned source, effective native and consumer macro fingerprints, actual DLL hashes and response-file `/arch`/FP flags. No instruction-profile fallback is silently selected.
2. Rebuild the entire native consumer module. Run existing foundation/servo/rig/body/joint/query and shutdown tests; retain all current hard PHAT angles, masses/inertia, collision filters and query receivers.
3. Run explicit one-/two-agent live smoke and current actual-NN 100-agent workload: 22 bodies/21 joints/88 bones each; real CPU models at 30 Hz; 60 Hz physics/presentation; capsule movement/feedback; completed-pose callbacks; post-EndPhysics queries; generation-safe teardown. No exact Chaos/SSE2 trajectory gate is added.
4. Compare repeated SSE2/AVX2 runs with the same P-class GT diagnostic, workers, movement-only profile, query padding, DuringPhysics/batching flags and sample counts. Report total-world and Jolt phases, CPU placement, median/p95 and all samples. AVX2 may change CPU frequency or contention; a native-only gain does not prove a whole-pipeline gain.

The current native Update phase is about 2.15 ms of a roughly 12.2 ms actual-NN world interval. That phase is the main possible beneficiary, so there is no evidence that AVX2 alone can close the complete gap below 10 ms. Its benefit, if any, must be measured without reducing quality or cadence.
