## Non-Negotiable Working Rules

**NEVER DO, IMPLEMENT, CHANGE, TEST, OPTIMIZE, VALIDATE, OR EXPAND ANYTHING THE USER DID NOT EXPLICITLY ASK FOR. NEVER INFER MATERIAL INTENT OR DETAILS. IF SOMETHING MATERIAL IS UNCLEAR, STOP AND ASK BEFORE ACTING.**

**KEEP THIS JOURNAL TO THE FINISHED CURRENT PRODUCT: durable rules, accepted implementation, authoritative paths, keeper settings, verified measurements, real remaining risks, and the next handoff. Do not append turn-by-turn history, failed attempts, speculative diagnoses, or obsolete alternatives. Replace stale text. Git preserves history.**

**USE LIVE CODING FOR UNREAL C++ CHANGES. NEVER CLOSE OR RESTART UNREAL UNLESS THE USER EXPLICITLY AUTHORIZES IT. If Live Coding is blocked or fails, stop and ask before closing or restarting.**

**WITH OBJECT REINSTANCING ENABLED, reflected header changes (`UFUNCTION`, `UPROPERTY`, `USTRUCT`, `UENUM`, `UDELEGATE`, etc.) are not by themselves a reason to restart. Try Live Coding first, including for new Blueprint nodes. Restart only after an actual failed/invalid patch and explicit user authorization.**

- For nontrivial Unreal engine, animation, rendering, physics, MetaHuman, asset-pipeline, or performance work, first check current Epic documentation, UE 5.7 source, and relevant established reports. Do not invent a replacement before checking the supported route.
- If visual/runtime evidence contradicts the implementation model, stop stacking patches and investigate the exact symptom again.
- Use numerical captures for temporal/follower behavior when they answer the question directly. The user performs the final visual check faster; do not spend time staging screenshots unless requested or a still image is genuinely diagnostic.
- Keep Unreal changes surgical. Do not save unrelated dirty levels/assets, dismiss material dialogs on the user's behalf, or change project/engine settings without an explicit request.
- Use `apply_patch` for source/journal edits. Preserve unrelated working-tree changes.
- Live Coding cannot migrate the layout of already allocated, non-UObject private data. Keep implementation storage behind stable owning pointers and avoid changing live allocation layouts; reflected UObject reinstancing alone does not protect those allocations.
- For normal Editor builds intended to support subsequent Live Coding, omit `-NoLiveCoding`: it changes the compile definition `WITH_LIVE_CODING` to 0. Alternating it with Live Coding (1) rewrites generated headers and causes broad rebuilds even when the Live Coding request is canceled. Use the normal Editor target with `-WaitMutex -NoHotReload`, without that flag. ## Physical Simulation And Magnetization

- Physical mode is real Chaos simulation: rigid bodies travel under forces/torques and constraints and can collide during travel. It does not teleport limb colliders to authored targets.

- Per-body settings are stored in `Body Magnetization Settings`:

  - `bMagnetizationEnabled` enables the native follower for that body.
  - `LinearStrengthScale` and `AngularStrengthScale`: `1.0` exact accepted correction, `0.5` half correction, `0.0` disables that correction axis.
